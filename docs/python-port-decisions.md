# Python port: decisions log

Decisions taken autonomously during the bash to Python port (ADR 0022), so
they can be reviewed after the fact. Newest at the bottom of each section.

## Process

- 2026-10-12. Each sub-phase (1 to 12) gets its own commit as soon as its tests
  pass, as the user authorized. Messages are a single line with no attribution.
- 2026-10-12. After every 3 sub-phases (3, 6, 9, 12) the main session runs two
  reviews over that span's diff: a code review (`ecc:code-reviewer` plus
  `ecc:python-reviewer` where Python changed) and an adversarial review whose
  goal is to break the change: edge cases, races, behavior drift from bash,
  secret leaks. CRITICAL and HIGH findings are fixed in a separate `fix:`
  commit before the next sub-phase starts.
- 2026-10-12. The project rule "do not start a new phase branch until the
  previous one is merged" conflicts with "finish everything". Resolution:
  phase branches are stacked. Phase B branches off the tip of phase A and so
  on, each branch is pushed with `-u` and a compare URL is reported (gh PR
  creation does not work with this token). The user merges in order A, B, C, D.
  If A changes after review, B is rebased onto it.
- 2026-10-12. This file is committed together with the sub-phase it belongs to,
  so it is visible on GitHub from the pushed branches.

- 2026-10-13. The connect timeout applies only when it is shorter than the overall request timeout. Otherwise a stuck connect is a plain "timeout", so the two kinds cannot race at the same instant.
- 2026-10-13. A connect that times out is the new kind "unreachable" (curl exit 28 style, status 8 `UNREACHABLE`, Python only). Failover treats it as a model failure and moves on at once.
- 2026-10-13. No route to the host or network (ENETUNREACH, EHOSTUNREACH, EHOSTDOWN, ENETDOWN) is also "unreachable", because the host cannot be reached either way. A refused connection stays "connect" (status ERROR): the host is up, so the normal cooldown fits.
- 2026-10-13. DNS resolution is not covered by the connect timeout (getaddrinfo has no timeout). It stays bounded by the overall timeout.
- 2026-10-13. Breaker: an unreachable failure counts toward the same threshold as other failures (default 3) and then pauses the model for `SHUNT_BREAKER_UNREACHABLE_COOLDOWN_SECONDS` (config field `unreachable_cooldown_seconds`, default 120). With a 5 s connect timeout the sleeping-laptop case costs about 15 s before the model is paused, which is acceptable, and a single flaky connect does not pause a model. `breaker.limits()` keeps its two values, a separate `unreachable_cooldown()` resolves the new one (env, config, default).
- 2026-10-13. The dashboard breaker line now also carries `unreachable_cooldown_seconds=<n> default=120`. The `shunt-breaker-config` command is not extended (the field is set by editing the config file or the env var).
- 2026-10-13. An invalid `SHUNT_CONNECT_TIMEOUT` is a CONFIG problem of the call (`shunt: SHUNT_CONNECT_TIMEOUT must be a number, got 'x'`), raised before any request is sent, so the model is skipped without a breaker failure.
- 2026-10-13. Part B, healthcheck. `providers.json` gets an optional boolean `healthcheck` per provider (default false). A non-boolean value is a validation error (`provider "x": healthcheck is not a boolean (true or false)`). `providers-write set` keeps the field of an existing entry (the CLI flag came later, see below).
- 2026-10-13. The check is `GET {base_url}/models` with the chat request's auth header, the connect timeout of part A and `SHUNT_HEALTHCHECK_TIMEOUT` (default 3 s, `0` disables). Healthy is any status below 500. The body is capped at 4 KiB and never read or logged. A too large body still counts through the status that came with it.
- 2026-10-13. A failed check is `shunt: <model> healthcheck failed: <reason>` with status UNREACHABLE, so failover and the short breaker cooldown apply. Reasons are fixed texts (`HTTP 503`, `connect error`, `no answer in time`, `no connection in time`), never a header or body.
- 2026-10-13. The check runs once per model attempt, before the first request, also for a chunked call. Its timeout is cut to the time left of the total deadline, and a timeout that came from that cut is DEADLINE, not UNREACHABLE.
- 2026-10-13. Cache: `~/.cache/agent-model-shunt/healthcheck.json` (override `SHUNT_HEALTHCHECK_CACHE_FILE`), entries of provider, base_url (trailing slash dropped) and epoch seconds, at most 64. `SHUNT_HEALTHCHECK_TTL` default 60 s, `0` writes and reads nothing. Time comes from the breaker's `now()`, so `SHUNT_NOW_EPOCH` works in tests. Read with O_NOFOLLOW and O_NONBLOCK, refused unless a regular file owned by us, at most 64 KiB. Written through a 0600 temp file and `os.replace`, skipped when the path is a symlink. Any read or write problem is ignored.
- 2026-10-13. Invalid `SHUNT_HEALTHCHECK_TIMEOUT` or `SHUNT_HEALTHCHECK_TTL` is a CONFIG problem, raised only for a provider that has the healthcheck on and before any request. The three validators share one helper in env.py with unchanged messages.
- 2026-10-13. Dashboard: a provider line ends with `healthcheck=on|off` while the providers file is valid.
- 2026-10-13. `provider set --healthcheck on|off` (bash parses it, `providers-write set` gets it as an optional sixth argument). A new entry without the flag gets `"healthcheck": true`, an existing entry without the flag keeps its value, absent included. The runtime default in `providers.py` stays off for a missing field. The OpenCode migration puts `"healthcheck": true` in the entries it creates (also the pending opencode ones), but when the provider already has the field in providers.json, `migrate_view.providers_doc` keeps the existing value. The model-config skill offers the choice next to key storage and passes the flag in `provider set`.
- 2026-10-13. The check now covers the model, not only the server, in two steps. Step 1 is `GET {base}/models`: 5xx, timeout or no connection is unhealthy. A 200 with a JSON `data` list of objects with `id` must contain the model id (the part after `provider/`, as sent upstream), else the reason is `model not listed`. An unparseable list or a 4xx skips the step, because some servers have no `/models`. Step 2 is `POST {base}/chat/completions` with `{"model", "messages": [ping], "max_tokens": 1, "stream": false}` and the same auth header.
- 2026-10-13. Step 2 rule: any 2xx is healthy, 400 and 422 too (the model route answered, for example a reasoning model that rejects `max_tokens`), and so are 401, 403 and other 4xx but 404, consistent with step 1 where the real call reports the auth error. 404, 5xx, timeout and no connection are unhealthy, with the reasons `model HTTP <n>`, `model gave no answer in time`, `no connection in time`. The /models list is read up to 1 MiB, the completion answer up to 4 KiB.
- 2026-10-13. New `SHUNT_HEALTHCHECK_MODEL_TIMEOUT`, default 30 s (a local server may load the model first), validated like the other numbers (EnvError, a CONFIG problem), `0` skips step 2. It is cut by the total deadline like the first timeout, and a cut model probe is a DEADLINE stop. `SHUNT_CONNECT_TIMEOUT` applies to both steps.
- 2026-10-13. The success cache key is provider, base_url and model id, and the file keeps its version. Entries get a `model` field, old entries without one never match and age out. Only success is cached, as before.
- 2026-10-13. The probe's tokens are not written to the usage log. The probe is a plain HTTP call in `healthcheck.py` and does not go through the usage accounting of the real request.

## Benchmark rerun with healthcheck

- 2026-10-13. The rerun measures only the delegate side (no Claude calls), with a driver script in the scratchpad that reuses `evals/benchmarks.json` and `evals/fidelity-questions.json`. The code-write tasks are three new small ones (pytest, json, bash), so they compare the two sides but not the previous report.
- 2026-10-13. v0.5.0 accepted the `healthcheck` field, so both sides used the real providers file. A models copy with only the delegate under test enabled keeps failover from hiding a failure. Breaker state, healthcheck cache and usage log are per side in the scratchpad.
- 2026-10-13. Spark went down during the run. The partial Spark data is reported as is, a second full attempt was not repeated because each bash call would wait the full timeout. The outage is reported as the unreachable-delegate measurement. The simulated outage points the Spark provider copy at 10.255.255.1 and uses mac as the failover target, because mac was awake.
- 2026-10-13. Timeout cap of 120 s (`SHUNT_TIMEOUT_SECONDS` and `SHUNT_TOTAL_TIMEOUT_SECONDS`) for the unreachable runs, 300 s for the normal runs.
- 2026-10-13. Healthcheck off the request path. User decision: the check must never slow a normal request. The synchronous `healthcheck.check` is gone. A request calls `healthcheck_bg.gate`, which only reads the status cache. Probes run in a detached child.
- 2026-10-13. Cache entries are now `{provider, base_url, model, status, at}` with `status` `healthy` or `unhealthy` and `at` the time of the check. An old entry without `status` is read as healthy, so no migration is needed. The file safety rules are unchanged (own regular file, O_NOFOLLOW, atomic 0600 write, symlink skipped).
- 2026-10-13. Gate rules. Fresh unhealthy (younger than `SHUNT_HEALTHCHECK_RETRY`, new, default 30 s): UNREACHABLE at once, no probe. Healthy fresh (younger than `SHUNT_HEALTHCHECK_TTL`, default raised from 60 to 600 s): nothing. Unknown or stale: the real call goes on and one background probe starts. Decision for the open case: an unhealthy entry older than the retry time is not blocking, the real call acts as the recheck and a probe also starts. A clock that went back (negative age) counts as stale. TTL `0` starts a probe on every call (deduped by the lock), RETRY `0` never blocks.
- 2026-10-13. The child is `python -I -B shunt_main.py healthcheck-refresh -- <provider> <model>`, started with Popen, `start_new_session`, DEVNULL streams and `close_fds`. Only the provider name and the model id are in argv. The child reads the providers file and the key itself, as the transport does, and gets the parent's environment unchanged. The `--` keeps a model id that starts with a dash from being read as an option. Any spawn error is swallowed and the lock freed.
- 2026-10-13. Dedupe: a lock file `.healthcheck-<sha256 prefix>.lock` in the cache dir, made with O_CREAT|O_EXCL|O_NOFOLLOW, 0600, taken by the parent before the child starts and removed by the child. It is stale after twice the probe's time cap and then replaced (two spawners racing for a stale lock may both win, which costs one extra probe). The cap is the two probe timeouts plus two connect timeouts plus 5 s. The child sets SIGALRM to that cap, always exits 0 and stays silent.
- 2026-10-13. The real call updates the status once per attempt on success (healthy, `at` refreshed) and on every UNREACHABLE (unhealthy). Other statuses leave it alone. Only for providers with the healthcheck on. The gate's own UNREACHABLE does not count, so an unhealthy entry still ages out.
- 2026-10-13. For a provider with the healthcheck on, a refused connection (`connect`) and a failed name lookup (`dns`) are also UNREACHABLE (they were a plain error). A model behind a VPN that is down looks like that. Providers without the healthcheck are unchanged.
- 2026-10-13. Breaker interplay (user requirement: a model is out only until its unhealthy entry expires). Chosen: for a provider with the healthcheck on (and `SHUNT_HEALTHCHECK_TIMEOUT` above 0), failover does not record an UNREACHABLE failure in the breaker at all. The status cache owns it, and it expires after the retry time. The alternative, capping the cooldown at RETRY, was not taken because the breaker has a threshold and a file lock and would still need a state entry to clear. A good probe clears the breaker state of the model (the plain key and every `#role` key) like a success. Other failures still count as before.
- 2026-10-13. Warm-up: the session-start hook calls `healthcheck_bg.warm_up` after the text is rendered. It starts a probe for each enabled model of a healthcheck provider whose status is missing or stale, never waits, and swallows every error. The hook output and exit code are unchanged. The module avoids importing the transport, so the hook starts as fast as before. The base_url rule (https assumed when there is no scheme) is repeated in `base_url_of` for that reason.
- 2026-10-13. `SHUNT_HEALTHCHECK_INLINE=1` runs the probe in the calling process, for tests only. The tests never start a child except the `healthcheck-refresh` command test, which waits for it.
- 2026-10-13. The total deadline no longer covers the check, since the request does not run it. `SHUNT_HEALTHCHECK_TIMEOUT` and `_MODEL_TIMEOUT` apply to the probe only. An invalid TTL or RETRY is still a CONFIG problem before the request, an invalid model timeout shows only in the child (silent).
- 2026-10-13. Warm-up starts ONE detached child for all due models, not one per model: `healthcheck-refresh -- <provider> <model> [<provider> <model> ...]`. The parent takes each model's lock first (dedupe is unchanged), the child probes them one after the other and frees each lock. Its time cap is the per-probe cap times the number of models. A lock of a model late in the queue is judged stale after twice the per-probe cap, so a very slow queue may see one duplicate probe. Sequential, because a fixed small parallelism was not needed for a handful of models.
- 2026-10-13. The child's time cap is a daemon `threading.Timer` that frees the locks still held and calls `os._exit(0)`. The earlier SIGALRM exception could be swallowed by a broad `except` in the HTTP client. A lock with an mtime in the future counts as stale. The probe frees its lock on every path, including the early returns for a changed provider flag or an unusable base_url.
- 2026-10-13. For a provider with the healthcheck on, HTTP 404 and 5xx from the real completion are UNREACHABLE (the model is unloaded or the server is broken), mark the model unhealthy and are not recorded in the breaker. TIMEOUT and DEADLINE never change the status: a long reply is not a health signal. Without the healthcheck these stay plain errors.
- 2026-10-13. After a successful real call on a healthcheck provider the model's breaker state (plain key and every `#role` key) is cleared, like after a good probe, so an older breaker pause does not linger while the status is healthy. A write problem is ignored.
