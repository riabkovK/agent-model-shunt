Shunt Ledger

What it costs Claude to read a file directly, versus delegating the read to scripts/bulk-read and only keeping the answer in context.

n = 3 iterations per scenario fixtures: real Go source, labstack/echo v5.3.1 baseline model: claude -p --model sonnet real spend this run: $3.80

How this was measured

Three scenarios, each run three ways, over the same question and the same file(s):

no-resume
Claude reads the file(s) directly, in a brand-new claude -p session. The cost of a one-off question with no prior context.
resume
Same question, chained into the same Claude session as the previous scenario via --resume. The cost of reading one more file in a session that's already open.
shunt
scripts/bulk-read delegates the question and file(s) to a separate model over OpenCode; only its answer lands in Claude's context.

Reported tokens for no-resume/resume are Claude's real input + cache_read + cache_creation usage; for shunt they're a chars/4 estimate of just the delegate's answer text (a best case - it excludes the tokens a live session spends emitting the tool call that routes to it). Cost is real dollars billed by the Claude API, which is a more honest comparison than raw token counts: a large, roughly constant share of every token count here (tens of thousands of tokens) is this project's own Claude Code system prompt and tool/skill/hook definitions, not the fixture file - that overhead is repriced far down once it's served from prompt cache (see resume below charging less than no-resume for a similar token count), so cost tracks reality better than tokens do.

Operating notes

Shunt is much slower on real code than the token savings alone suggest.

All three scenarios here use real, unmodified files from a production Go codebase (150-960+ lines each) rather than short synthetic snippets. Against files that size, the delegate model routinely took 40-160+ seconds per call - roughly 3-4x longer, in absolute terms, than the entire no-resume Claude call it's replacing. This is why SHUNT_TIMEOUT_SECONDS now defaults to 300s: at the old 120s default, 5 of the first 9 shunt calls in this run timed out outright, and every scenario needed a re-run before reaching n=3. Even at 300s, expect the latency trade-off on files this size to be measured in tens of seconds to minutes, not the single-digit seconds a short-file demo might suggest.

Speed depends on your provider, not on shunt itself.

The shunt timings above were measured against one specific OpenCode provider and model. Different providers/models can be dramatically faster or slower for the same call, and gateway load varies over time. These numbers are a personal observation from one setup at one point in time, not a guaranteed baseline - run evals/baseline-benchmark.sh against your own provider before trusting these figures to describe your own flow.

Reproduce: ITERATIONS=3 evals/baseline-benchmark.sh from the repo root (needs a reachable OpenCode provider and a logged-in claude CLI; spends real money on your Claude account). Fixture provenance: evals/fixtures/echo/NOTICE.md. Raw data: evals/results/baseline-benchmark-summary.json.
